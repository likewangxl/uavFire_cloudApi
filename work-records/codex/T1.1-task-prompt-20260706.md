# T1.1：修复"异步补图成功后未重报热事件"缺陷（T1 补丁）

## 缺陷描述（评审发现）

T1 把热事件上报改为"先报警（thermalImageUrl 可空）、快照异步补传"。但后端语义如下：

- `DualStreamServiceImpl.java:787-791`：thermal 通道事件温度达标但 `thermalImageUrl` 为空 → reviewStatus 置 `THERMAL_IMAGE_MISSING`，`confirmedThermalFireEventIdByTask.remove(...)`，**不创建 fire_event**。
- `DualStreamServiceImpl.java:710-716`：可见光确认事件到达时，取 `thermalTriggerByTask` 里存的热触发事件，若无热图 → 同样置 `THERMAL_IMAGE_MISSING` 并提前返回，**不创建 fire_event**。

而 T1 的 `ThermalHotspotMonitor.retryThermalSnapshotAfterReport` 补图成功后**只调用了 `launchVisibleSnapshotConfirmation`，没有把带 URL 的热事件重报给后端**。后端存的热触发事件永远是无图版本 → 快照首传失败的场景下 fire_event 永远建不出来。旧流程（阻塞重测直到有图才上报）虽然慢但最终能建 fire_event，因此这是功能回归，必须修复。

## 修复要求（仅 rcplus-msdk-agent）

1. `ThermalHotspotMonitor.retryThermalSnapshotAfterReport`：补图成功后，先用相同的 `taskId`/`droneSn`/`sourceTs`/温度/ROI/measurements 再调一次 `client.recordThermalHotspotEvent`（这次带 `thermalImageUrl`），让后端刷新热触发事件；然后再 `launchVisibleSnapshotConfirmation`。
   - 注意重测路径：若走了 `sessionManager.measureThermalHotspot` 重测且拿到新温度/区域，重报应使用重测得到的温度/区域/measurements（保持数据与快照一致）。
   - 首次上报用的温度/区域/measurements 需要传入 retry 函数（当前签名只传了 seedRegion，需补参数）。
2. 单测（ThermalHotspotMonitorTest）：
   - 快照首传失败、补传成功场景：`recordThermalHotspotEvent` 被调用两次，第二次 `thermalImageUrl` 非空，且随后触发可见光确认。
   - 补图彻底失败场景：只报一次（URL 为空），不触发可见光确认（维持 T1 行为）。
   - 快照首传成功场景：只报一次（URL 非空）。
