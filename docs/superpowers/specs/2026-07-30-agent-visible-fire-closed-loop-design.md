# RC Plus Agent 可见光火情识别与定位闭环设计

日期：2026-07-30

分支：`feature/agent-fire-detection-runtime`

## 1. 决策摘要

生产火情链路不再使用 `ai-service`。RC Plus Agent 是唯一的实时识别与飞行定位执行端：

```text
MSDK 可见光原始帧
  → Agent 本地 NCNN YOLO
  → 本地视觉确认
  → 本地暂停航线并稳定悬停
  → 本地重新识别 ROI 与 tap zoom
  → 本地激光三样本定位
  → 本地持久化事件、证据和待上报消息
  → 异步上报业务后端
  → 安全条件满足后自动恢复原航线
```

业务后端继续负责火情事件存储、空间合并、告警通知、任务管理、驾驶舱展示和人工控制，但不再通过逐步命令推进悬停、ROI 重捕获或激光测距。

RTMP/ZLMediaKit 只服务驾驶舱直播，不参与识别和飞行控制。

## 2. 目标

- 使用 MSDK 可见光 RGBA 原始帧在 Agent 本地执行正式 YOLO 检测。
- 同时支持 `fire` 和 `smoke`，两类目标都执行悬停、ROI 重捕获、tap zoom 和激光定位。
- 将网络、后端响应、RTSP、截图写盘从“识别到悬停”的关键路径中移除。
- 视觉确认后第一时间在后端创建事件并发出提醒，不等待悬停或激光定位完成。
- 激光成功时精确更新同一事件；激光失败时仅上报飞机观测位置，不伪造火点坐标。
- 定位流程结束并可靠保存上报任务后，自动恢复原航线继续巡检。
- 断网、App 重启和重复上报时不丢事件、不重复建事件、不重复通知。
- 所有页面状态、定位方法和飞行状态使用中文展示。

## 3. 非目标

- 不把火情事件数据库、空间合并、告警、任务管理或驾驶舱迁入 Agent。
- 不保留 `ai-service` 作为生产影子检测器或降级检测器。
- 不让后端参与正常定位会话的逐步编排。
- 不把飞机 OSD 经纬度当作火点经纬度。
- 不以现有 640 输入热成像模型的 NCNN 成绩替代 960 输入可见光模型的实机验证。
- 不在本次迁移中顺便改变已验证的可见光阈值，除非新的实机准确率门禁要求调整并留下证据。

## 4. 系统职责边界

### 4.1 Agent

Agent 独占以下实时职责：

- 可见光相机源和帧新鲜度校验；
- 容量为一的最新帧缓冲；
- 模型加载、哈希校验、预处理、NCNN 推理和 NMS；
- `fire` 火色像素校验；
- 连续帧和 ROI 空间一致性确认；
- 航线暂停、稳定悬停和断点恢复；
- tap zoom 后使用新鲜帧重新识别 ROI；
- 激光启停、样本校验和坐标结果；
- 会话状态、证据文件和 Outbox 本地持久化；
- 进度与结果异步上报；
- 看门狗、崩溃恢复和飞行安全裁决。

### 4.2 业务后端

后端继续负责：

- 启动或停止整个监测任务；
- 校验 Agent、任务、模型和策略身份；
- 幂等接收 Agent 事件与进度；
- 火情事件、历史和任务持久化；
- 精确定位后的空间合并；
- 告警通知与通知去重；
- 地图、列表和详情展示；
- 人工终止、保持悬停或恢复等高优先级操作。

后端不得在正常 Agent 会话中下发 `visible-fire-hold`、等待 ROI、再下发激光命令。现有 `VisibleFireLocalizationDispatcher` 必须退出 Agent 主模式的创建事件路径。

### 4.3 ai-service

- 生产启动清单中不再启动 `ai-service`；
- 后端火情监测启动/停止不再创建或查询 ai-service 检测任务；
- 后端不再接受 ai-service 产生的正式生产火情事件；
- 迁移期可以保留源码和离线验证工具，但不得接入生产运行路径；
- 稳定验收后再单独清理无用运行代码，避免迁移与大规模删除混在一个变更中。

## 5. Agent 本地检测规则

### 5.1 模型和运行时

- 使用当前生产可见光 `fire/smoke` 权重作为迁移源模型；
- 生成可复现的 ONNX、TFLite 和 NCNN 产物及哈希清单；
- 现有基准框架可以复用，但必须用可见光模型和可见光验证集重新执行；
- 只有通过可见光召回率、P95、30 分钟稳定性和正式 APK 共载门禁的运行时与模型才能进入生产；
- 生产 APK 只包含一个推理运行时和一个正式模型；
- 事件中必须携带模型 SHA-256、模型版本、策略版本、输入尺寸、APK 版本和运行时版本。

### 5.2 帧策略

- 只接受当前 MSDK 可见光源的 `RGBA_8888` 帧；
- 最新帧缓冲容量固定为一，替换时释放旧帧；
- 同时只允许一个推理执行；
- 推理、截图、上传和后端调用不得阻塞 MSDK 帧回调；
- 常态目标为有效推理率不低于 5 FPS，消费帧龄 P95 不高于 300ms；
- tap zoom 后只能使用动作完成时间之后的新帧重新识别 ROI。

### 5.3 视觉确认

单帧命中只在 Agent 内形成候选，不向后端告警。

正式视觉确认至少要求：

- 连续两张新鲜帧达到生产置信度阈值；
- 两帧最高分目标的归一化中心距离符合策略；
- `fire` 类通过与当前 Python 生产逻辑一致的火色像素校验；
- `smoke` 类不执行火色像素否决；
- 帧源、模型、推理器和本地存储均健康。

RGBA 与 OpenCV BGR 的通道差异必须通过金样本测试显式验证，不能直接翻译阈值代码后假定结果一致。

## 6. 本地定位状态机

主要状态：

```text
DISARMED
  → ARMING
  → SCANNING
  → VISUAL_CONFIRMING
  → VISUAL_CONFIRMED
  → HOLD_REQUESTED
  → HOVER_VERIFYING
  → TARGET_ALIGNING
  → LASER_MEASURING
  → RESULT_DURABLE
  → RESUME_REQUESTED
  → SCANNING
```

任意不确定、人工接管或安全异常进入：

```text
MANUAL_HOLD
```

### 6.1 暂停与悬停

- 视觉确认后，Agent 先持久化会话和首条 Outbox，再请求暂停；
- 航线任务存在时暂停当前任务，否则执行悬停；
- 水平速度不高于 0.3m/s、垂直速度绝对值不高于 0.2m/s，并连续稳定 1 秒后进入目标对准；
- 暂停和悬停调用必须幂等；
- 无法在 8 秒内确认稳定悬停时进入 `MANUAL_HOLD`。

### 6.2 fire 和 smoke

`fire` 与 `smoke` 均执行完整的 ROI 重捕获和激光定位。

- `fire` 定位结果页面显示为“明火目标定位点”；
- `smoke` 定位结果页面显示为“烟雾观测定位点”；
- 烟雾是半透明目标，激光可能落在烟雾后方物体上，页面必须提示“可能不是实际起火源”；
- 两类事件都保留原始类别、置信度历史、ROI、图片和定位解释字段。

### 6.3 ROI 重捕获与激光

- Agent 使用本地检测器提供的新鲜 ROI，不再从后端轮询 ai-service ROI；
- tap zoom 后等待相机稳定，再使用动作完成时间之后的新帧重新推理；
- 最多执行三轮“对准—重捕获—落点检查”；
- 激光落点必须位于最新 ROI 内；
- 定位成功要求连续三个 `NORMAL` 样本；
- 样本间隔 300ms，地理散布不超过 15m；
- 成功结果的默认误差半径为 5m，并保留三个原始样本。

## 7. 第一时间提醒与分阶段上报

同一火情只使用一个由 Agent 生成的稳定 `eventId`。视觉确认和定位结果是同一事件的不同阶段。

### 7.1 阶段一：立即告警

第二帧完成视觉确认后，Agent 在同一个本地事务中写入：

- 火情会话；
- 当前状态；
- 首条轻量 JSON Outbox；
- 证据文件引用。

事务成功后并行执行：

1. 本地暂停/悬停；
2. 立即向后端创建事件。

初次事件：

```text
detectionStatus = VISUAL_CONFIRMED
locationStatus  = LASER_LOCATING
flightStatus    = HOLD_REQUESTED
fireLat/fireLng = null
```

初次请求不得等待 JPEG 编码、图片上传、稳定悬停或激光结果。正常网络验收目标：

- 视觉确认到后端事件提交不超过 1 秒；
- 视觉确认到驾驶舱提醒不超过 1.5 秒。

后端在同一数据库事务中写入火情事件、历史和通知 Outbox，提交成功后才返回 ACK。首条通知文案为“发现疑似火情，正在精确定位”。

### 7.2 阶段二：进度

Agent 可以异步上报：

- `HOLD_REQUESTED`
- `HOVER_STABLE`
- `TARGET_ALIGNING`
- `LASER_MEASURING`
- `RESUME_REQUESTED`
- `MISSION_RESUMED`

进度用于驾驶舱展示和审计，不增加火情通知版本，不阻塞本地状态机。

### 7.3 阶段三：定位成功

Agent 使用同一 `eventId` 更新：

```text
locationStatus = PRECISE
geoMethod      = LASER_RANGEFINDER
fireLat/fireLng/fireAlt = 激光结果
```

后端验证激光样本后更新同一事件、写历史、执行空间合并并更新地图和任务。通知版本递增一次，原通知更新为“目标已完成激光定位”，不创建第二条独立火情告警。

### 7.4 阶段四：定位失败降级

激光失败时：

```text
locationStatus = DEGRADED_OSD
geoMethod      = AIRCRAFT_OBSERVATION
fireLat/fireLng/fireAlt = null
aircraftLat/aircraftLng/aircraftAlt = OSD
```

后端保留视觉火情事件和告警。飞机 OSD 只能表示“发现火情时的飞机观测位置”：

- 不作为火点坐标展示；
- 不参与火点空间合并；
- 不用于自动抵近航线；
- 不使用精确火点图标；
- 不设置虚假的 5m 误差半径。

通知更新为“视觉火情已保存，激光定位失败，已记录飞机观测位置”。

## 8. 可靠性、顺序和幂等

Agent 本地至少持久化：

```text
fire_session
fire_evidence
report_outbox
```

每条消息包含：

- `eventId`
- `sessionId`
- `sequence`
- `eventTimestamp`
- `state`
- `modelHash`
- `policyVersion`
- `payload`

规则：

- `eventId` 全局唯一；
- `(eventId, sequence)` 唯一；
- 同一事件严格按 sequence 发送；
- 首次立即发送，失败按 250ms、500ms、1s、2s、5s 退避重试；
- 后端重复请求返回成功但不重复入库、通知或建任务；
- 旧 sequence 不得覆盖新状态；
- `PRECISE` 或 `DEGRADED_OSD` 不得被迟到的 `LASER_LOCATING` 覆盖；
- 图片独立补传，不提升通知版本；
- App 重启后恢复未完成会话和 Outbox；
- 无法确认飞行状态时恢复为 `MANUAL_HOLD`，不得猜测性继续航线。

## 9. 自动恢复航线

`fire` 和 `smoke` 在激光成功或降级结果可靠保存后都自动恢复原航线。

“可靠保存”定义为：

1. 会话、证据和最终结果已写入 Agent 本地持久化存储；
2. 最终上报已进入持久化 Outbox；
3. 已立即尝试发送后端；
4. 在线时最多等待后端 ACK 1 秒；
5. 1 秒未收到 ACK 时仍可恢复航线，Outbox 后台继续补报。

恢复前必须满足：

- 原任务、航线和暂停断点完整；
- 飞机仍处于稳定悬停；
- MSDK 状态允许恢复；
- 没有人工接管或保持悬停命令；
- 没有低电量、返航、避障或飞控异常；
- 激光已关闭，目标对准会话已结束；
- 没有其他未完成的本地火情控制会话。

恢复后必须等待 MSDK 确认航线重新执行。恢复失败或超时进入 `MANUAL_HOLD`，不得循环调用恢复。

## 10. 后端数据准确性规则

- 初次事件不得用 OSD 回填 `fireLat/fireLng`；
- `LASER_LOCATING`、`DEGRADED_OSD` 和其他未解析定位状态不得参与空间去重；
- `PRECISE` 坐标必须来自通过校验的激光样本；
- 飞机位置始终写入独立 `aircraft*` 字段；
- 后端校验 Agent 身份、任务状态、模型允许列表、时间、ROI、sequence 和状态转换；
- 后端以事件状态机拒绝非法回退和相互矛盾的终态；
- Agent 上报的检测历史和激光原始样本作为不可变审计证据保留。

建议将现有“OSD 缺失坐标回填到火点坐标”的逻辑对 Agent 未解析事件显式禁用。

## 11. 中文页面映射

数据库和接口保留稳定英文码，页面、通知和地图图例统一映射为中文。前端使用一个共享映射模块，禁止各页面自行维护重复判断。

| 状态码 | 中文 |
|---|---|
| `VISUAL_CONFIRMED` | 可见光火情已确认 |
| `LASER_LOCATING` | 正在激光定位 |
| `PRECISE` | 已完成激光定位 |
| `DEGRADED_OSD` | 仅有飞机观测位置 |
| `HOLD_REQUESTED` | 正在暂停航线 |
| `HOVER_STABLE` | 飞机已稳定悬停 |
| `TARGET_ALIGNING` | 正在对准目标 |
| `LASER_MEASURING` | 正在激光测距 |
| `RESUME_REQUESTED` | 正在恢复航线 |
| `MISSION_RESUMED` | 已恢复航线 |
| `MANUAL_HOLD` | 等待人工处理 |
| `REJECTED` | 已排除误报 |
| `AIRCRAFT_OBSERVATION` | 飞机观测位置 |
| `LASER_RANGEFINDER` | 激光测距定位 |

要求：

- 未映射状态显示“未知状态”，不得直接展示英文码；
- 测试枚举所有后端状态，缺少中文映射时失败；
- 列表、驾驶舱、详情、地图和通知使用一致含义；
- 状态同时使用文字、图标和颜色，不能只依赖颜色；
- `DEGRADED_OSD` 必须显示“飞机观测位置，非火点精确位置”；
- `smoke + PRECISE` 必须显示“烟雾观测定位点，可能不是实际起火源”。

## 12. 安全优先级

固定优先级：

```text
人工接管 / 遥控器摇杆
  > DJI 低电量、返航、避障等安全动作
  > 紧急终止
  > 火情定位闭环
  > 自动恢复航线
```

检测器崩溃、状态冲突、存储不可写、任务断点丢失、飞控状态未知或恢复失败时，不得自动继续航线。

## 13. 验收门禁

### 13.1 模型与准确率

- 使用固定可见光正负样本集对 PyTorch 与 NCNN 逐样本比对；
- 召回率相对 PyTorch 下降不超过 2 个百分点；
- 单独验证小火、烟雾、夜间暗部、火色否决和 zoom 后 ROI；
- 验证 `fire` 与 `smoke` 的类别和坐标一致性；
- 禁止仅为性能把输入从 960 降为 640 而不重新通过召回门禁。

### 13.2 正式 APK 性能

在 DJI UX、可见光解码和 RTMP 推流同时运行时：

- 推理 P95 不超过 200ms；
- 有效推理率不低于 5 FPS；
- 消费帧龄 P95 不超过 300ms；
- 连续运行 30 分钟无崩溃和持续内存增长；
- 最后 5 分钟 P95 相对前 5 分钟退化不超过 20%；
- UI、推流、MSDK 回调和飞行控制无可观察卡顿。

### 13.3 上报与恢复

- 正常网络下首次事件入库不超过 1 秒，驾驶舱提醒不超过 1.5 秒；
- 断网、超时、重复请求、乱序和 App 重启不丢事件；
- 同一 `eventId` 只产生一个正式事件和一个首次告警；
- 图片失败不阻塞首次告警；
- 激光成功只更新同一事件；
- 激光失败不生成火点坐标；
- ACK 超过 1 秒不阻塞安全恢复；
- 恢复成功必须有 MSDK 状态证据，恢复失败进入 `MANUAL_HOLD`。

### 13.4 飞行验证

- 先做静态台架和无桨安全验证；
- 再验证暂停失败、悬停不稳、ROI 丢失、激光失败、断网、后端重启、Agent 重启和人工接管；
- 分别用 `fire` 与 `smoke` 目标验证定位和恢复；
- 受控实飞验证事件提醒、坐标语义、原航线断点恢复和重复火点处理；
- 未通过任一安全门禁时，Agent 检测模式不得默认启用。

## 14. 迁移顺序

1. 将现有热成像迁移分支重新基线到当前纯可见光生产代码；
2. 完成可见光模型导出、基准集和 RC Plus 实机运行时门禁；
3. 实现 Agent 最新帧、检测器和视觉确认策略；
4. 实现本地持久化状态机、悬停、ROI 重捕获、激光和恢复；
5. 实现分阶段幂等上报与后端通知 Outbox；
6. 取消后端激光分步调度和 ai-service 运行依赖；
7. 完成中文状态映射和覆盖测试；
8. 通过集成、断网、重启、台架和受控实飞门禁；
9. 从生产启动清单移除 ai-service；
10. 稳定运行后单独清理遗留 ai-service 生产代码。
