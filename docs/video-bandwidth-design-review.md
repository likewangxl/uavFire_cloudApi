# 视频分级方案评审记录

日期：2026-09-05。分支：`codex/video-bandwidth-4hd-16sd`。方式：对照当前源码、SDK 接口和异常时序进行本地评审，非现场验收，也非独立人员签字。

## 开发前评审

结论：修订以下问题后，可进入分支内开发与自动验证；不承诺仅凭软件消除物理网络瓶颈。

| 问题 | 修订决定 |
| --- | --- |
| 旧方案无人观看停流不符合本次选择 | 本期保持 20 路持续上传，仅切输出编码档位 |
| 先升新机、再降旧机会超出四路 | 授权名额保留到租约到期，并增加 10 秒设备降档/回调保护期；最多四个保留名额 |
| 后端重启可能忘记仍有效的高清 | 启动隔离窗口为 15 秒租约＋10 秒保护期；明确单实例调度前提 |
| 网络等待阻塞本地过期处理 | 独立轮询与看门狗；Agent 使用请求发起时的单调时钟，迟到响应不延长租约 |
| 档位下发复用长时飞行命令会排队 | 独立身份绑定视频策略接口，不占飞行/激光队列 |
| 多人同时选高清可能绕过全局预算 | 观看接口只提交需求，后台统一排序；一个页面离开不清除其他页面需求 |
| 低码率可能误改本地 AI 帧输入 | 只操作 ILiveStreamManager，不改相机/帧消费者；真机必须比较输入帧尺寸、帧龄 |
| SDK 的设置成功不等于网络实际发送符合预算 | 区分请求档位、应用结果、SDK 原始观测、浏览器接收码率；正式容量验收增加 ZLM 入站证据 |
| 混装旧 APK、同 SN 多进程、多活后端会破坏保证 | 登记机群、检测实例冲突；发布验收核对全部 APK 和单实例，不将这些情形标为覆盖完成 |

“四路”的软件保证是对新版参与者的授权/保留名额约束。若 SDK/操作系统完全挂起，软件看门狗无法保证物理流立即降档；需通过真实设备故障测试与服务器入站观测判断，不能把超时参数当作硬实时保证。

## 开发后复审

结论：**代码评审及本期自动验证通过，可交付地面测试版本；现场部署验收待完成。** 前端仍有 24 项 main 基线既有失败，正式发布前须处理相关项或记录其验收结论，不能将全量前端标为通过。

### 已处理的实现问题

- 两端以单调时钟计算授权，不依赖跨机器时钟一致；HTTP 迟到、身份切换及旧请求失败均不能延长旧高清授权。
- 后端并发申请、旧授权保护期、启动隔离、同 SN 多实例冲突均有确定性测试。状态接口将最新目标、尚未消退的旧高清授权及 Agent 报告分开，避免把降档等待误报为新高清申请。
- 身份绑定策略接口挂入 Agent 专用鉴权；观看/状态接口保留用户鉴权和工作区过滤；MockMvc 验证 snake_case 请求/响应。已验证火情才参与优先级，保留原证据确认顺序。
- SDK start/stop/档位更新使用同一互斥锁；档位不变不重复设置；设置失败先回 LOW，LOW 也失败时只停止网络推流。本地取帧绑定未改，仍须真机证明 SDK 内部没有影响输入。
- 页面隐藏/销毁取消订阅和连接；增加异步创建代次保护，迟到播放器立即关闭；有新帧才视为播放健康，连续 5 秒无新帧触发既有有限重试策略，仅重连异常画面。
- 浏览器码率按字节计数差分计算，计数重置和缺失保持未知；不将 ICE RTT 或抖动缓冲标成端到端延迟。
- Agent 版本更新后，同步既有版本断言；播放器重构后更新重复拉流的接线断言，并增加共享源只提供一个播放 URL 的行为校验。

### 发布前必须闭合的事实

1. 在每个目标机型/遥控器/负载组合上实测 SD/500,000 bit/s 和 FULL_HD/4,000,000 bit/s，包括正在直播时改档、切镜头、断网、SDK 报错。SDK 编译与 getter 回读不证明物理输出码率或分辨率。
2. 核对 20 台 APK/进程身份、真实飞机 SN 和唯一调度实例。旧 APK、未登记额外源、多活后端及完全挂起的设备不在授权上限的软件保证内。
3. 采集 ZLM 入站、出口、每台上行及浏览器数据，验证 20 机和多观众；真实可用容量不足时先补链路或重新调整两档参数，不能靠增大播放缓存达到实时。
4. 两档切换前后核对本地 ONNX 输入尺寸、帧龄、识别与证据送达。保留现有未验收机型/飞控门禁。
5. 完成 [部署验收表](../deployment/video-bandwidth/README.md) 的 1 → 4 → 20 机测试及 30 分钟端到端延迟趋势；没有这些记录，不宣称“彻底消除延迟”或“已经上线”。
